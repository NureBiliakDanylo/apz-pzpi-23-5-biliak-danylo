2 ЗАВДАННЯ
В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система. Вимоги до оформлення Звіт повинен містити: - опис стратегії масштабування системи; - опис технічних рішень які роблять масштабування можливим; - аналіз вузьких місць — які саме ресурси вичерпуються першими при навантаженні; - опис навантажувальних тестів з ілюстрацією зв’язку між масштабуванням і витримуваним навантаженням. Будь-які конфігурації серверів, налаштування навантажувальних тестів, тощо необхідно завантажити на GitHub.

3 ОПИС ВИКОНАНОЇ РОБОТИ
1. Мета роботи
Провести навантажувальне тестування розгорнутого API за допомогою Artillery, продемонструвати переваги горизонтального масштабування (збільшення кількості контейнерів).
2. Виконані налаштування для сервера
А. Масштабування інфраструктури (Docker Compose):
Кількість екземплярів API збільшено з 1 до 5 за допомогою команди “--scale api=5”. Це дозволило розподілити обчислювальне навантаження між декількома контейнерами Node.js.
Б. Оптимізація балансувальника навантаження (Nginx):
Параметр “worker_connections” збільшено до 10 000 для обробки великої кількості TCP-з'єднань. Впроваджено динамічне розпізнавання адрес (resolver 127.0.0.11) та використання змінних у “proxy_pass”. Це вирішило проблему кешування DNS і забезпечило рівномірний розподіл запитів (Round Robin) між усіма п'ятьма контейнерами API.
В. Налаштування бази даних (PostgreSQL):
“max_connections” збільшено до 1000, щоб база могла приймати запити від усіх інстансів API одночасно. Вимкнено “synchronous_commit” для прискорення операцій запису на диск під час тестів. Збільшено об'єм “shared_buffers” до 256MB для кращого кешування даних.
3. Методика тестування (Artillery)
Було налаштовано сценарій з поступовим зростанням навантаження (Ramp-up) до 30 нових користувачів на секунду. Загальна кількість віртуальних користувачів у тесті склала приблизно 2200 за 160 секунд. Сценарій включав реєстрацію датчика та циклічну відправку показників температури, вологості та тиску.


4. Результати тестування
Завдяки балансуванню через Nginx, навантаження на CPU розподілилося рівномірно між усіма контейнерами, що можна було побачити у статистиці docker при тестах. Оптимізація лімітів бази даних та Nginx дозволила значно знизити відсоток помилок порівняно з початковими тестами. Горизонтальне масштабування довело свою ефективність: система залишається більш стабільною при навантаженнях, які були занадто критичними для одного контейнера.
