2 ЗАВДАННЯ
На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи. Вимоги до оформлення Звіт повинен містити: - UML діаграму прецедентів (Use Case Diagram); - UML діаграму компонент (Component Diagram). - Не менше ніж дві діаграми, на вибір, із вказаних: - ER-модель даних (Entity–Relationship Model) мобільної платформи; - UML діаграму пакетів (Package Diagram); - UML діаграму взаємодії (Interaction Overview Diagram); - UML діаграму діяльності (Activity Diagram); - UML діаграму станів (State Diagram). Код мобільного застосунку необхідно завантажити на GitHub перез захистом роботи.

3 ОПИС ВИКОНАНОЇ РОБОТИ
1. Мета
Метою роботи було розробити мобільний застосунок на платформі Android, який є частиною системи інтернету речей (IoT) та взаємодіє з центральним сервером для отримання та відображення даних з сенсорів, а також прогнозів.
2. Технології
Технологічний стек:
- Мова програмування: Kotlin
- UI фреймворк: Jetpack Compose (Material 3)
- Мережева взаємодія: Retrofit 2 + Gson
- Локальне сховище: Jetpack DataStore (Preferences)
- Графіки: Vico Charts
3. Архітектура застосунку
Застосунок побудований за принципами чистій архітектури та шаблону MVVM:
- UI Layer (Screens): Набір Composable-функцій, що відповідають за відображення інтерфейсу ("SetupScreen", "SensorListScreen", "SensorDetailScreen", "SettingsScreen").
- ViewModel Layer ("IoTHubViewModel"): Керує станом інтерфейсу, обробляє бізнес-логіку (наприклад, фільтрацію пошуку або вибір одиниць температури) та координує роботу з репозиторієм.
- Data Layer:
- Repository ("IoTHubRepository"): Єдине джерело даних, яке динамічно створює екземпляри API-сервісу при зміні URL сервера.
- API Service ("IoTHubService"): Опис REST-ендпоінтів для взаємодії з сервером.
- Local Storage: "ServerSettingsManager" (налаштування сервера, мова, одиниці вимірювання) та "FavoriteSensorsManager" (збережені ідентифікатори сенсорів).
4. Інженерні рішення
4.1. Динамічна конфігурація сервера
Оскільки застосунок повинен працювати з приватними інстансами IoT-хабів, реалізовано "SetupScreen" для першого входу та можливість зміни URL у налаштуваннях. Репозиторій автоматично переналаштовує Retrofit при зміні базової адреси.
4.2. Локалізація та інтернаціоналізація
Реалізовано підтримку двох мов (Українська, Англійська). Для коректної зміни мови "на льоту" застосунок використовує "AppCompatDelegate" та ресурси конфігурації.
4.3. Конвертація одиниць вимірювання
Сервер передає дані температури виключно в градусах Цельсія. Для зручності користувача реалізована утиліта "TemperatureUtils", яка на боці клієнта перераховує дані в Кельвіни або Фаренгейти залежно від налаштувань.
4.4. Гнучкий прогноз
Реалізовано можливість вибору часового проміжку для прогнозу (від 1 до 24 годин). Застосунок валідує введення користувача та виконує запит до API з параметром "hours_ahead".
4.5. Пошук та фільтрація
Для роботи з великою кількістю сенсорів додано функціонал пошуку за назвою або локацією, що працює в реальному часі за допомогою фільтрації потоку даних (StateFlow) у ViewModel.
5. Взаємодія з системою
Мобільний застосунок взаємодіє з сервером через REST API за наступними протоколами:
- "GET /sensors" – отримання списку всіх доступних сенсорів.
- "GET /sensors/{id}/readings" – отримання історії останніх показників (температура, вологість, тиск).
- "GET /local-forecasts/{sensor_id}?hours_ahead={n}" – отримання прогнозованих значень на вказаний період.
